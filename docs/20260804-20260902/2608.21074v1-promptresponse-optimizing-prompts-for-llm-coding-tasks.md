## 摘要
大型语言模型（LLMs）在研究工作流程和软件开发流水线中的应用日益广泛，但其输出仍然对输入提示的变化敏感。本文介绍了“PromptResponse”这一受控研究，考察提示的格式化方式以及基于LLM的调优如何影响所生成代码的性能、效率和稳定性。我们使用HumanEval数据集的五种语义相同但句法不同的变体——基线、JSON、Markdown、YAML以及一个LLM调优版本——让GPT-4o在超过8200次执行中解决其编码问题。我们的结果表明，一致的格式化——尤其是JSON——提高了生成效率和句法稳定性，同时在任务性能上有小幅提升。相反，LLM调优后的提示导致任务性能显著下降，而在任何其他维度上均无显著改善。这些发现表明，仅低成本的重新格式化就能带来可测量的改进，而调优必须考虑模型对齐。我们最后根据研究结果提供了一套实用建议，并发布了我们的数据集变体和评估流水线以供未来研究使用。

## Abstract
Large language models (LLMs) are increasingly used in research workflows and software development pipelines, yet their output remains sensitive to input prompt variations. This paper presents $\unicode{x00AB}$PromptResponse$\unicode{x00BB}$, a controlled study examining how formatting and LLM-based tuning of coding task prompts affect the resulting code's performance, efficiency, and stability. Using five semantically identical yet syntactically distinct variants of the HumanEval dataset$\unicode{x2014}$baseline, JSON, Markdown, YAML, and an LLM-tuned version$\unicode{x2014}$we had GPT-4o solve its coding problems over 8200$\unicode{x00A0}$executions. Our results show that consistent formatting$\unicode{x2014}$especially JSON$\unicode{x2014}$improves generation efficiency and syntactic stability, with minor gains in task performance. Conversely, the LLM-tuned prompts resulted in significantly degraded task performance without significant improvements in any other dimension. These findings suggest that low-effort reformatting alone can yield measurable improvements, while tuning must account for model alignment. We conclude our work with providing a set of practical recommendations informed by our results as well as releasing our dataset variants and evaluation pipeline for future work.

## 2. 方法论

### 2.1 核心思想
通过控制单个独立变量——提示数据集的结构形式（DATASET）——在**语义完全一致、句法/格式不同**的五种提示变体下，让同一 LLM（GPT-4o）重复完成同一批编码任务，从而分离提示格式与调优方式对输出质量、效率、稳定性的因果效应。

### 2.2 自变量的五个水平
| 水平 | 名称 | 说明 |
|---|---|---|
| 1 | `vanilla` | 原始未经修改的 HumanEval 提示（基线），存在较多内部结构不一致、拼写错误与排版问题 |
| 2 | `json` | 将 HumanEval 提示解析为结构化 JSON，所有字段全部显式包含（空段为空/[]），233 KB |
| 3 | `markdown` | 使用 Markdown 标题/表格/代码块/加粗重排的版本，空字段填 "None"/"Not specified"，218 KB |
| 4 | `yaml` | 使用 YAML 列表/映射结构的版本，空段留空作为字符串，209 KB |
| 5 | `tuned` | 用 **Mistral-7B-Instruct-v0.2** 对原提示 docstring 进行改写调优的"改进版"，保留函数签名，212 KB |

其中 `json`、`markdown`、`yaml` 三者的信息内容与原始短文完全一致（包括未被修正的拼写错误）；`tuned` 则是用另一个 LLM 按照系统指令（只重写 docstring、不修改签名、不写实现）进行语言层面的调整，内部格式也被标准化。

### 2.3 请求协议
每次 API 请求统一采用两段消息前缀：
- **System**："You are a Python programming expert."
- **User**："Please solve the following problem. Output only the function with the signature as specified in the prompt and all necessary imports. Do not include additional texts or comments."

### 2.4 因变量（评估指标）
| 类别 | 指标 | 含义 |
|---|---|---|
| 任务性能 | **PASS RATE（pass@1）** | 每提示的 10 次生成中通过全部 HumanEval 测试用例的比例 |
| 效率（生成） | **GEN DURATION** | 从发送 API 请求到接收完整回复的时长（受服务器负载影响） |
| 效率（代码运行） | **EVAL DURATION** | 在本机用 Python 执行测试用例的总运行时长 |
| 效率（正确代码运行） | **PASS DURATION** | 仅统计通过测试用例的执行在 EVAL DURATION 上的结果 |
| 代码长度 | **RESPONSE LEN** | 生成代码的字符数 |
| 句法稳定性 | **ROUGE-L** | 同一提示 10 次生成回复之间两两的 ROUGE-L 均值（衡量字符级一致程度），范围 0–1 |

### 2.5 统计分析框架
- 因 Shapiro–Wilk 正态性检验全部显著偏离正态 → 采用非参数检验；
- 主效应检测：**Kruskal–Wallis 检验**，效应量用 ε²（按 Cohen 建议分类：小 >0.0099、中 >0.0588、大 >0.1379）；
- 事后两两比较：**Mann–Whitney U 检验 + Bonferroni 校正**，效应量报告秩双列相关 r（小 >0.10、中 >0.30、大 >0.50）。

## 3. 实验设计

### 3.1 数据集与基准
- 唯一基准数据集：**OpenAI HumanEval**（164 个人工编写的 Python 函数级编码问题），及其四个派生版本（json / markdown / yaml / tuned），总共 5 个条件。
- 每个提示运行 10 次以获得稳定性估计，总执行次数：5 数据集 × 164 提示 × 10 重复 = **8,200 次**独立 API 请求。

### 3.2 被测模型与对照方法
- 生成模型：**OpenAI GPT-4o**（gpt-4o-2024-08-06），使用默认温度与默认 API 设置（不自定义任何参数），理由是普通用户通常不会修改默认设置；
- 调优模型：**Mistralai/Mistral-7B-Instruct-v0.2**（由论文作者用于生成 tuned 提示），默认温度。
- 各条件之间仅在提示语法/结构层面存在差异，内容语义等价；无多智能体、CoT 等额外外部方法对照。

### 3.3 执行流程
1. 先构建五个数据集变体；
2. 依次对每个数据集的每个提示发起 10 次全新会话（无历史上下文）的 ChatGPT API 请求；
3. 记录每次回复及其 GEN DURATION；
4. 实验后，用单独脚本清理响应（去掉 ```python 等包装）、拼接辅助函数、调用 `exec()` 执行测试用例，记录 ROUGHLY 代码运行的通过/失败、RESPONSE LEN 和 EVAL DURATION；
5. 对同一提示的 10 次执行进行聚合，计算 PASS RATE、PASS DURATION、ROUGE-L。

## 6. 主要结论与发现

### 6.1 任务性能（PASS RATE）
- 各条件平均 pass@1：**json 0.901 > markdown 0.890 > vanilla 0.886 > yaml 0.873 > tuned 0.748**。
- Kruskal–Wallis 检验显著（χ²(4) = 19.18, p < 0.001, ε² = 0.019，小效应）。
- **关键发现**：tuned 显著差于 vanilla（p = 0.045）、markdown（p = 0.006）和 json（p = 0.002）；而 json/i.markdown 相对 vanilla 的增益不显著。
- 结论：**LLM 调优提示在本设置中并未提升、反而明显损害了任务性能**；格式化带来的性能提升微弱且不确定。

### 6.2 生成效率（GEN DURATION）
- 显著的主效应（χ²(4) = 35.05, p < 0.001, ε² = 0.038）：yaml 最快（1.37s），随后是 markdown（1.44s）、json (1.49s)，vanilla 和 tuned 最慢（均为 1.61s）。
- 结构清晰格式（json/markdown/yaml）的生成时间显著短于 vanilla 和 tuned。
- 结论：**一致的格式化（即使提示字符数增加）能提高生成阶段效率**；而 LLM 调优未能带来该收益。

### 6.3 代码运行效率和代码长度（EVAL / PASS DURATION, RESPONSE LEN）
- EVAL DURATION、PASS DURATION 和 RESPONSE LEN均未发现显著差异（p 分别 = 0.283、0.413、0.849，ε²≈0）。
- tuned 的平均 EVAL/PASS 时长最小，但主要因为它失败率高，放弃了大量困难耗时的测试任务（如 /129），因此**不能将 tuned 视为更高效**。
- **结论：提示格式对生成代码的执行效率和代码长度没有可验证的影响——不同格式“没有坏选择

——不同格式“没有坏选择”（no bad choice）”。

### 6.4 句法稳定性（ROUGE-L）
- Kruskal–Wallis 检验显示不同数据集对生成回复的句法稳定性存在显著影响：χ²(4) = 42.84, p < 0.001, ε² = 0.047（中等偏小效应）。
- 事后两两比较发现：**json（中位数 ≈ 0.93）和 markdown（≈ 0.92）显著高于 vanilla（≈ 0.88）与 tuned（≈ 0.87）**；yaml（≈ 0.90）居中，但与 vanilla 的差异未达到校正后的显著水平。
- 结论：**将提示改写为结构清晰、语义无歧义的格式（尤其是 json 和 markdown）能显著提升 LLM 多次生成间的一致性**；而经过 LLM 调优的 tuned 提示在生成本身上并未带来更稳定的回复，反而与原始提示相当或更差。

## 7. 讨论

### 7.1 为何结构化格式比原始提示更好？
- 原始 HumanEval 提示中的注释位置不固定、无统一字段结构，模型需要自行“理解”哪些是函数定义、哪些是示例、哪些是约束。
- 使用 json/markdown/yaml 显式分割区域后，任务意图更易被模型“定位”，因此表现出更稳定的生成结果和略高的 pass@1。
- 然而，结构化格式带来的性能提升幅度很小（约 +1 ~ +2 个百分点），且未通过多重比较校正后的显著性检验，提示**格式优化的收益存在上限**。

### 7.2 为何 LLM 调优（tuned）大幅变差？
- Mistral-7B 对 docstring 的改写虽然保持了语义，但可能引入了**隐含的风格变化**（如更详尽的描述、更多限制性措辞），而 GPT-4o 对这类“外来”文风并不总是更适应。
- 这揭示了“自动提示调优”的潜在风险：用一个小模型优化的提示未必适合另一个大模型，**模型间对齐不足可能抵消甚至逆转调优收益**。
- 作者将 tuned 的低效归因于调优模型与生成模型的策略或训练数据分布不匹配，而非 Mistral 本身的能力缺陷。

### 7.3 效率与性能的权衡
- 生成效率方面，结构化提示（尤其是 yaml）能显著缩短响应时间，但其根源可能是更紧凑、更不拖沓的文本表达降低了模型逐字生成的开销；
- 这种效率收益并没有以牺牲正确性为代价——yaml 与 vanilla 的 pass@1 差异并不显著；
- 因此在实际工程中，**选择结构清晰的提示格式是一个“免费午餐”**：能提升稳定性与生成速度，且不损害功能正确性。

## 8. 研究局限与未来工作

### 8.1 主要局限
- **单模型、单基准**：仅使用 GPT-4o 与 HumanEval，结论难以推广到其他 LLM、真实软件仓库或复杂多文件任务；
- **调优变量混杂**：tuned 条件由 Mistral-7B 生成，不能在完全可控条件下回归“仅 LLM 调优”这一因素；
- **时间指示依赖服务器**：GEN DURATION 受网络/负载影响较大；
- **未进行超参数寻优**：使用默认温度，但未探索温度对稳定性影响的交互；
- **ROUGE-L 的局限**：该指标只能反映表层 token 重叠，不能度量代码语义等价性（如不同变量名/重构后的逻辑等价代码会被判低相似度）。

### 8.2 未来方向
- 在更多 LLM（如 Claude 系列、Llama 系列、本地小模型）上重复实验，建立跨模型的提示偏好地图；
- 使用更强/同族的调优模型（如 GPT-4o 自身调优）检验“模型-提示对齐”假说；
- 将研究扩展到真实仓库级任务（如 SWE-bench）以考察格式效应在更大上下文中的表现；
- 设计语义级一致性评估指标（如单元测试迁移率）来替代 ROUGE-L。

## 9. 总体结论

- 在 HumanEval 风格代码生成任务中，提示的结构格式（json/markdown/yaml）相比原始文本能带来**微弱且不显著的正确性增益**，但能**显著缩短生成时间和提高输出稳定性**；
- 用另一个 LLM（Mistral-7B）进行自动“语言润色”并未提升、反而显著损害了 GPT-4o 的任务性能（pass@1 降低约 14 个百分点）；
- 没有任何提示变体在代码运行效率（EVAL/PASS DURATION）或生成代码长度上造成显著差异；
- 总之，**“如何组织提示”比“如何措辞提示”更值得关注**；便宜的离线模板化格式化（json/markdown）是安全且有效的提示工程增强手段，而任意的 LLM 自动调优需要谨慎评估与目标模型的兼容性。
